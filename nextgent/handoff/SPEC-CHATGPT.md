# NEXT GENT spec: ChatGPT's architecture (the owner's chosen version) + the owner's rules

The owner says these are the correct documents. Code is judged against THIS file, not against Claude's plan or CONTRACT.md where they differ. Where this file flags "OPEN", the owner has not decided; report the code's choice as needing a decision.

## A. Three sources of truth
1. **Paperclip owns PLATFORM state:** account, user, company/workspace, agents, workers, tasks/work, **routines/automations**, approvals, activity, **costs**, store catalog, store versions, company installations, update channel, update policy, permissions, and eventually the **logical device association** (which computer/phone belongs to which company). "Do not build another control plane."
2. **gcr-api-clean (+ the cyber check Supabase database) owns BUSINESS state:** business, parent/child business, identity, hours, locations, contacts, services, menus, prices, availability, bookings, events, photos, reviews, staff, policies, FAQs, payments detected, integrations; plus the public MCP, the private/business MCP, GCR directory data, concierge data. Answers "what IS this business". Not recreated inside Paperclip.
3. **The local runtime owns MACHINE state:** Android state, browser sessions, local files, local calendar cache, App Maps, local configuration, device state, execution journal, verification evidence. Not another cloud source of business truth.
- The two databases are separated on purpose: Paperclip/Saas = platform; cyber check = business. Platform things must not be put in the business database.

## B. Eight areas, four surfaces
Areas: (1) Paperclip control plane; (2) Store + release lifecycle (Paperclip `nextgent/foundation`: store_items, store_item_versions, store_installs, store_install_resources, store_settings; stable/fast channels; automatic/manual; security/bugfix/enhancement advisories; required security updates); (3) business data (gcr-api-clean + cyber check); (4) declarative app runtime (App-build- manifest + shared renderer; NOT its own login/Supabase/store); (5) agents/workers (Paperclip owns agent record and work; worker = Hermes/OpenClaw/Codex/other adapter; Jarvis = human-facing conversational doorway, not the policy engine; one boss: Paperclip, not Hermes Kanban too); (6) local execution: nextgent-platform (ALLOW/ASK/DENY, approvals, dispatch, Android control, SIM messaging, browser, Linux, fresh verification, execution journal, receipts, relay client, MCP capability tools); (7) App Maps: nextgent-maps (`maps/environment/application/capability/version/map.yaml`, data, versioned; a Facebook UI change ships a new map, no executor rebuild); (8) appliance/system distribution: nextgent-ghost-image (pinned repos/commits, install, health check, atomic switch, rollback, signed releases, block updates). Two update systems, never combined: cloud product updates through the Paperclip store; local machine updates through nextgent-ghost-image.
Surfaces (presentations, not architectures): Play-user (customer web/mobile), Boxes (TV/computer, a surface not a boss), Plat-admin (operator), GCR/gcr-unified (public; reads gcr-api-clean directly, not through Paperclip).

## F. Apps, connectors, data (capability model)
- Apps are capabilities, not industries or vendors (one Availability, one Menu, one Listings, one Book…). The app declares the normalized concept it needs; connectors map sources (POS, CRM, calendar, booking system, spreadsheet, email, API, iCal, manual, device observation) into it. Apps never rewritten per vendor.
- An installed app contributes a public front end and an owner back end over the same data; plus data it uses/creates, settings, actions. Owner dashboard's app area is assembled from installed apps; uninstalling removes both surfaces.
- One canonical business-data system. Apps read shared business data and create only app-specific records (song_requests, crowdsource_sessions/options/votes, shoutout_requests, merch products/orders, gallery_items, reviews, listings…), all scoped to the business/install, on the business-data side. No database per app.
- Canonical identity (our internal id) + source identity (source, source_id/external ids, SKU) for every record; provenance (source_type, source_id, external_record_id, source_updated_at, last_synced_at, created_by, updated_by, owner_override) so syncs update instead of duplicating and never overwrite owner corrections.
- **The App Store does not own app business data.** Paperclip knows installed/version/enabled/entitled. A lightweight runtime projection (business_app_instances: business_id, installation_id, app_key, enabled, public_enabled, render_mode, public_label, config) on the business side lets public pages render without calling Paperclip per page load; it is NOT a second store.
- Public page = assembly of installed modules (install/remove/reorder/hide/show/render as button, inline, own page); page shell owns branding/theme/order.
- Agents read through the business MCP/API, no private copies. Automations react to events (booking.created, review.created, song_request.created, availability.changed, order.created, lead.created…); **"Paperclip owns the routine/control logic. CyberCheck owns the actual booking/review/customer state."**
- Physical Android is the hand for outside systems, never the business database.

## G. Owner's rules (binding)
- Don't stack or duplicate pieces. Where code sits today doesn't mean it belongs there. Nothing hard-coded (industries, business names, categories, URLs, prices, plans, models, phone numbers, emails, providers, limits). Bookings, QR menus, song requests, link pages are apps, not built in. Emails are FORWARDED by the business, never caught/pulled. Agents run in the cloud. Businesses choose their agents and apps. Directory, concierge and phone assistant are separate interfaces over one business data/MCP. Reuse existing code; never drop a feature without full replacement. Examples/prototypes are for understanding, never copied. Design decisions are the owner's.
- Telephony: not Twilio.
